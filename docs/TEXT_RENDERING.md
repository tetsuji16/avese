# 文字描画の差異と改善方針

描画画像の文字は `src/engine/raster.rs` で `ab_glyph` のアウトラインを tiny-skia の画像へ合成する。原作の Windows GDI とは画素単位では一致しない。WMF/EMF はフォント名とスタイルだけを記録し、表示側の GDI に描画を委ねるため、ラスタ画像との一致も保証しない。

## GDI との差異（現在把握しているもの）

- ビットマップフォント（System、Terminal、Fixedsys）は持たず、MS ゴシックで代用する（`candidates` の対応表）。字形・幅は原作と異なる。
- ヒンティング: `ab_glyph` はアウトラインを直接塗り、ヒンティングを適用しない。小サイズで GDI より線が太く・薄く見える可能性がある（GDI との画素比較は未実施）。
- アンチエイリアス: 灰階調の被覆率ブレンド。GDI の設定（ClearType 等）との比較は未実施。線や図形は従来どおりアンチエイリアスなし。
- 字送り: `h_advance` とカーニングを小数のまま積算する。GDI がデバイス単位に丸めるかは未検証。
- ベースライン: フォントの ascent を丸めずに用いる。GDI の丸めとの差は未検証。
- 太字・斜体: 実フォントがあればそれを使い、ないスタイルだけ合成する（下記）。MS ゴシック・MS 明朝には太字・斜体のファイルがなく、常に合成になる。

## 今回実施したこと

- 太字・斜体の実フォントを先に探す。確認した対応（`C:/Windows/Fonts` に存在）: Arial（arialbd/ariali/arialbi）、Times New Roman（timesbd/timesi/timesbi）、Courier New（courbd/couri/courbi）、Tahoma（tahomabd のみ）、Verdana（verdanab/verdanai/verdanaz）、Segoe UI（segoeuib/segoeuii/segoeuiz）、メイリオ（meiryob.ttc のみ）、游ゴシック（YuGothB.ttc のみ）。
- 実フォントが提供するスタイルには合成をかけない。提供しないビットだけ二重描画（太字）または傾き（斜体、`ITALIC_SHEAR`）で補う。例: Tahoma の太字斜体は tahomabd の実太字に斜体のみ合成。
- 文字ごとのフォールバックは従来どおり。フォールバック先の面は実スタイルを持たない扱いで、必要なスタイルを合成する。フォントキャッシュのキーは (パス, コレクション番号) なので面ごとに区別される。
- Linux/macOS: 一致するファイル名のうち、`bold`/`italic`/`oblique` を含む名前で要求スタイルに合うものを優先し、なければ通常面＋合成。この経路は Windows 上で実行できず、未検証。
- `measure_text` を描画と一致させた。合成太字のときだけ幅に +1px、合成斜体のときだけ左にベースライン下の張り出し（descent × 0.21）、右に ascent × 0.21 を加える（端数列の配分を含め切り上げ）。アンカー（左・中央・右）は測定した箱を基準にし、インクは箱の中に収まる。
- テスト: 描画した画素の列が測定幅の箱内に収まること（Arial / MS ゴシック / Tahoma、標準・太字・斜体・太字斜体、左・中央・右揃え）、合成時のみ幅が増えること、実太字面が合成と異なる描画になること。フォント未導入の環境では何もせず通過する。
- 目視確認: Arial、Times New Roman、MS ゴシック、メイリオの 4 スタイルを描き、Arial と Times では太字・斜体が実フォントの字形（斜体の a や g が筆記体形）であること、MS ゴシックは合成であることを画像で確認した。

## swash の評価

使い捨てのスパイク（リポジトリ外）で `ab_glyph` と比較した。msgothic.ttc、14pt、「これはサンプルデータです。 -760 780」、release ビルド、2000 回平均。

| 項目 | ab_glyph | swash（ヒンティングあり） | swash（なし） |
|---|---|---|---|
| 1 回の描画（フォント解析・コンテキスト生成を含む） | 33.3 µs（フォント解析は含まない） | 74.4 µs | 28.8 µs |

- バイナリ増加: ab_glyph のみの最小実行ファイル 278,016 B に対し swash のみは 1,281,024 B。差は約 1.0 MB（最小プログラムでの値で、本体への実増加は未測定）。
- 画質: ヒンティングありは縦方向の線がやや締まって見えた（主観）。実太字化（`embolden`）は動作したが、スパイクでは先頭の字の端が欠けた。原因は未調査。
- 判断: 速度は同程度から遅く、約 1 MB の増加に見合う明確な利得は確認できなかったため `ab_glyph` を維持する。実太字は面ファイルで足りる。ヒンティングが GDI の画素に近づくかは未検証。本プロジェクトは自作アルゴリズムより既存クレートを優先する方針であり、将来 GDI との画素比較で差の原因がヒンティングと判明した場合に再評価する。

## MS フォントの扱い

MS フォントは配布物に含めず、利用者の環境にインストールされたものを実行時に探して使う。代替フォントでの比較では、フォント名とバージョンを記録する。

## 残っていること

- 原作と同じ Windows・DPI・フォントで比較画像を収集し、字形と配置を分けて差を数値化する（字送りの丸め、ベースライン、ヒンティングの寄与を切り分ける）。
- Linux/macOS のスタイル付きフォント探索を実機で確認する。
- GDI 互換が必要な Windows 出力に GDI を使う経路を検討する。
- 下線・取り消し線はベースラインに沿った直線で、斜体でも傾けない（GDI と同じか未確認）。
